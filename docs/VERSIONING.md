# 版本命名规范

> **一句话**：有没有「功能更新」决定动哪一位 —— **有功能更新进次版本（+0.1.0），
> 没有就进补丁版本（+0.0.1）**；本仓的版本号是**仓库发布号**，
> 只在 [CHANGELOG.md](../CHANGELOG.md) 的版本标题里维护。

适用范围：本仓的**仓库发布号** —— [CHANGELOG.md](../CHANGELOG.md) 的版本标题、
Release 说明文件名、发版 tag，三处**必须一致**。

本仓是脚本仓库，**没有构建产物**：没有 `versionName` / `versionCode` 之类
从构建里读出来的版本号，别去任何配置文件里找它 —— 版本号是**手工维护的发布号**。

---

## 1. 三段式与进位规则

版本号是三段式：`主版本.次版本.补丁版本`（如 `0.1.0`）。

| 这次发版包含…… | 动哪位 | 写法 | 例子 |
|---|---|---|---|
| **没有功能更新** —— 只修 bug、改参数、改脚本内部实现、改文档 | **补丁版本 +0.0.1** | `x.y.z` → `x.y.z+1` | `0.1.0` → `0.1.1` |
| **有功能更新** —— 新增了使用者可感知的新能力，或现有能力的行为变了 | **次版本 +0.1.0**，补丁归零 | `x.y.z` → `x.y+1.0` | `0.1.0` → `0.2.0` |
| **破坏性变更** —— 现有用法不再成立（配置格式不兼容、调用方式变了、目标路径变化） | **次版本 +0.1.0**，并在 [CHANGELOG.md](../CHANGELOG.md) 的版本段落里**显式标注** | `x.y.z` → `x.y+1.0` | `0.1.0` → `0.2.0` |

进位是**连锁**的：次版本进位时补丁必然归零（`0.1.0` 的下一次功能更新是 `0.2.0`，
不是 `0.2.1` 也不是 `0.1.2`）。

## 2. 怎么判断「有没有功能更新」

判断口诀：**看使用者拿到的那份清单变了没有 ——**

- 使用者**能找到一个以前没有的东西**（新脚本、新 provider 分组、新文档入口），
  或者某个现有能力**改完参数和以前不一样了** → 有功能更新 → `+0.1.0`；
- 清单翻遍也找不到新东西，改的是「做得对不对」（修复）与「说得好不好」
  （文档措辞、注释、日志口径）→ 没有功能更新 → `+0.0.1`。

边界情况：

| 情况 | 算不算功能更新 | 理由 |
|---|---|---|
| 修一个「本该生效却没生效」的 bug | ❌ `+0.0.1` | 行为回到了它本来该有的样子，不是新行为 |
| 删掉某项能力 / 某个入口 / 某个 provider 分组 | ✅ `+0.1.0` | 能力清单变了，使用者可感知的减法也是更新 |
| 改了脚本的入参名、输出路径、默认行为 | ✅ `+0.1.0` | 调用方式变了，用法不再是原来那套 |
| 新增 / 删除一篇正本文档、给文档改名 | ❌ 连补丁版本都不给 | 见 §5：这类改动**根本不动版本号** |
| 只改文档内容、只修拼写、只动 CI 配置 | ❌ 连补丁版本都不给 | 同上 |
| 破坏现有用法（配置格式不兼容、目标路径变化） | ✅ `+0.1.0` + CHANGELOG 显式标注 | 见 §1 第三行 |

拿不准时问一句：**写 Release 说明时，会不会出现「新增 / 变更 / 移除了某能力」
这样的句子？** 会 → `+0.1.0`；全文只有「修复 / 调整 / 优化」→ `+0.0.1`。
再拿不准就问第二句：**这次发版，使用者拿到的东西比上次多了还是少了？**
多了 / 少了 → `+0.1.0`；没多没少 → `+0.0.1`。

## 3. 版本号在哪维护

**只有一处：[CHANGELOG.md](../CHANGELOG.md) 的版本标题**（形如 `## [0.1.0] — 2026-10-20`）。

本仓**没有构建产物版本号**，因此：

- 版本号**不从任何构建产物里读**，也没有第二个「真正的版本号」藏在别处 ——
  改版本号 = 改 [CHANGELOG.md](../CHANGELOG.md) 的段标题；
- 由它派生出两处**必须与标题一致**的引用：
  - Release 说明文件名 [docs/release-notes/0.1.0.md](release-notes/0.1.0.md)
    （格式正本见 [docs/release-notes/README.md](release-notes/README.md)）；
    文件名 = `versionName`，**不带 `v` 前缀**；
  - 发版 tag（`v0.1.0` 形式，tag 名 = `v` + 版本号）。

> 「文件名不带 `v`、tag 带 `v`」是本仓的既定口径：
> 说明文件是**按版本归档的文档**（名字就是版本号本身），
> tag 是**Git 标签**（沿用 `v` 前缀惯例）。改名只动文件，不要动 tag。

## 5. 不发版的时候：不动版本号

**不发版就不要动版本号。** 交付规则以本篇 §3 为唯一正本。

- **只改文档、只修拼写、只动 CI 配置 → 完全不动版本号**，连补丁版本都不给。
  这类改动只在 [CHANGELOG.md](../CHANGELOG.md) 顶部的 `## [未发布]` 段**追加一条**，
  **不新开版本段落**。
- 理由：版本号是给使用者看的「这次拿到了什么」的标记 —— 文档措辞、
  文件名规范化、流水线配置的修正都**不改变使用者拿到的东西**。
- 版本号特有的风险：**改文件名 / 改引用不算发版**。把
  `docs/release-notes/v0.1.0.md` 改成 `0.1.0.md`、把中文文档名改成全大写连字符，
  这类操作只动文件与引用，版本号与 tag 一律不动 ——
  顺手把版本号加一位，会把下一个正式发布号吃掉，事后得回头改 CHANGELOG 与 tag 对齐。

`[未发布]` 段攒够了再发版：把段标题改成 `## [x.y.z] — <发版日期>`，
并补一份同名的 Release 说明（`docs/release-notes/<x.y.z>.md`）。

## 6. 与 CHANGELOG 的关系

| 主题 | 唯一正本 | 其余位置怎么写 |
|---|---|---|
| **版本号本身**（当前是哪个版本、历史上有哪些版本） | [CHANGELOG.md](../CHANGELOG.md) 的版本标题 | 只留一句话 + 链接，不复制版本历史 |
| **进位规则**（下一次该动哪一位） | 本篇 §1 与 §2 | 只留一句话 + 链接，不抄表格全文 |

两处都写全文，迟早各改各的 —— 单一正本原则见 [docs/DOC-RULES.md](DOC-RULES.md)。
