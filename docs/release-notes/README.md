# release-notes/

> **一句话**：这里放**面向使用者**的 Release 说明 —— 形状、动词、覆盖率红线、
> 固定尾巴都在本篇定义，别的文档不重复。

放**面向使用者**的 Release 说明，文件名 = 版本号：

```
docs/release-notes/v0.1.0.md
```

发版时找 `docs/release-notes/<版本号>.md`；找不到就退回 `CHANGELOG.md` 的对应段落
（并在日志里 `::warning::` —— 那段是写给开发者的，使用者看到的是噪音）。

## 为什么要单独放一份

`CHANGELOG.md` 是**开发者记录**：症状 / 根因 / 改法 / 验证结果 / 踩坑史。
Release 说明是**给使用者看的**，要短、写成清单、只讲「我现在能拿到什么」。
两者受众不同，不能一份两用。

## 形状

**清单，不是文章。** 开头一句加粗说清这版是什么，紧接着一行反馈入口，
`## 本版内容` 下按分区一行一条，最后是固定尾巴。

```markdown
**首版：把 OpenCode-Go 套餐与 WorkBuddy2API 网关接进 ZCode，探测与同步脚本齐了。**

遇到问题、想要新功能，到 [Issues](https://github.com/MVennn/ZcodeAIModels/issues/new/choose) 反馈。

## 本版内容

**OpenCode-Go**

- 新增 六个 provider —— 主力 / 免费 / 低耗 / 高耗 / 对话 / 响应；按成本档分好组，模型列表见文档。

**WorkBuddy**

- 新增 三个 provider —— 免代 / 低代 / 高代；按积分倍率分层，组内从便宜到贵排。

**仓库**

- 新增 文档 —— 速查、参数矩阵、踩坑、排错、维护流程各一篇。

---

> 脚本会改你自己的 ZCode 配置文件（写前自动备份）。模型价格与额度以服务商当时的说明为准。
```

结尾那几行是**固定尾巴**，每版照抄不动。

### 反馈入口：写在开头，链接必须是绝对地址

第一行是加粗总结，**第二行是一行反馈入口**，然后才是 `## 本版内容`：

- 反馈入口**不是清单条目**（不写 `-`、不加粗），单独一行；
- 链接只能用绝对地址
  `https://github.com/MVennn/ZcodeAIModels/issues/new/choose` —— 同一份正文可能被转到
  别处，相对链接会落到错误的仓库；
- `issues/new/choose` 会先让用户选「问题反馈」还是「功能建议」，两类都收。

### 一条怎么写

```
新增 / 调整 / 修复 / 优化 + 对象名 —— 入口；一句话拿到什么
```

- **动词只有四个**：新增（以前没有）、调整（行为、默认值、位置变了）、
  修复（以前不对，**含底层与实现层**）、优化（使用者能感知的更快 / 更小 / 更顺）；
  另有「移除」用于删功能。都写全称 —— 单字「修」读着不像词。
- **对象名照抄配置里的东西**：provider 的显示名（主力 / 免费 / 低耗 / 高耗 / 对话 / 响应 /
  免代 / 低代 / 高代）、脚本文件名、文档名。不另起一个说法。
- **入口**写使用者在哪碰得到它（哪个 provider、哪个脚本、哪篇文档）；
  不需要找入口的（清单里一眼能看见），改写场景。
- **结果**一句说完，写使用者拿到什么。不写怎么用、不写为什么。
- 说人话。「`modelMatch` 是全匹配正则」这种只对开发者有意义的词别写；
  真要交代限制，写使用者看得见的后果（「模型列表里不刷新」）。
- 一行一条。两句才说得清 → 拆成两条，或者这条本来就该留在 CHANGELOG。

## 底层与内部改动：算「修复」，而且要拆开写

这条是给「使用者看不出区别、但代码确实改了」的改动定的。**它们也算本版内容，
必须写；而且要一条一条拆开，不许打包成一句。**

| 改了什么 | 动词 | 一行怎么写 |
|---|---|---|
| 底层缺陷（竞态、路径写错、限速不足、编码、时序） | 修复 | 写「以前会怎样」的后果，不写根因 |
| 重构 / 拆文件 / 收敛依赖（行为零变更） | 修复 | `修复 代码拆分 —— 哪几处拆开，行为零变更` |
| 删死代码、删悬空注释、清无用文件 | 修复 | `修复 死代码 —— 删了哪几处，行为零变更` |
| 日志 / 文案 / 注释口径纠错 | 修复 | 写纠了什么口径，不写讨论过程 |
| 仓库结构（目录重排、文档正本新增） | 调整 | `调整 仓库 —— …`；使用者不可见的也照写 |
| 使用者能感知的更快 / 更小 / 更顺 | 优化 | 写「快在哪」，并给数字 |

**禁止写法**：

- ❌ `优化 代码整理 —— 大文件按职责拆分、包依赖方向收敛，行为零变更`
  —— 三个改动压成一句，对不上 CHANGELOG，下个版本没人知道拆了哪些文件；
- ❌ `优化 稳定性 —— 中危 3 条、低危 10 条全部清零，细目见 CHANGELOG`
  —— 「细目见 CHANGELOG」等于没写，使用者和我们自己都不会去翻；
- ✅ 拆成 4~6 行，每行一个对象，行尾该标「行为零变更」的就标。

一句话记法：**凡是在 `git diff` 里出现过的东西，说明里都要有一行**。
写不长不是本事，漏的才是问题 —— 篇幅红线排在覆盖率之后。

## 覆盖率红线

**凡本版改过的东西，必须全部出现在 Release 说明里**，动词四选一（新增 / 调整 /
修复 / 优化），一行一条。没有例外：

- 缺陷修复 → 并进「修复」分组，一行写「修了什么 + 使用者可见的后果」
- 性能优化 → 并进「优化」分组；同类多项可归并成一行，但要列出对象
- 纯重构（行为零变更）→ 并进「修复」分组，**按对象拆成多行**（判据见上一节）
- 文档 / 声明类（README、NOTICE、第三方声明）→ 并进「仓库」分组，照写

写完拿 CHANGELOG 对应段落逐条对：**CHANGELOG 里的每一处使用者可感知的改动，
Release 说明里都得能找到对应行**。详细叙事留在 CHANGELOG，Release 说明只要一行短句。

### 篇幅

- 覆盖率红线优先于篇幅：先保证**一条不漏**，再谈合并。
- 分组按**接入线**走（OpenCode-Go / WorkBuddy / 仓库），不按轻重排。
- 合并手法：同类的接口调整并成一行；审查修复写使用者可见后果，不写根因长文。

## 别写这些

| 别写 | 为什么 |
|---|---|
| 第二人称叙述（「点一下就…」「你可以在…里改」「想换的话…」） | 使用者要的是有什么，不是操作步骤；步骤归 README |
| 「原来是这样，所以现在…」的原因与取舍 | 解释属于 CHANGELOG |
| 实现原理、取数口径、字段来源 | 同上 |
| 「关掉某开关」还是「默认开」这类通用信息 | 不随版本变 |
| 「之前是什么样」的对比 | 只有修复条目允许一句症状（「模型列表不刷新」），其余不写 |
| 「本版没有破坏性变更，直接覆盖安装」 | 没变更就不用声明；**有**的时候才必须写 |
| 凑数的「注意」区块 | 见下 |

## 「注意」区块：能不写就不写

只在**使用者不知道就会出问题**时才写，最多一两条：

- ✅ **有破坏性变更** —— 配置文件格式变了、旧的备份不能用、必须重新配。**必须写**。
- ✅ **已知的、会被当成新 bug 的问题** —— 例如某个 provider 还缺某个功能。如实写一条，
  免得被重复报。
- ❌ 每版都一样的操作提醒、性能说明 —— 不写。风险提示**例外**：
  每版说明末尾固定附提示段，属固定尾巴，不算重复内容。

## 固定尾巴（每版照抄）

```
---

> 脚本会改你自己的 ZCode 配置文件，写前自动备份到同目录的 .bak-* 文件。
> 模型价格、额度、倍率与可用性以服务商当时的说明为准；文档里的数字是快照，会过时。
```

风险与免责提示段按上面的模板**逐字粘贴、不随版本改写**（法律留痕：
持续提示、提示在先），它是固定尾巴的一部分，**不算重复内容**。

## 改已经发出去的说明

改完文案直接重写同一份文件、重新发布即可（同名文件会被覆盖）。
写完 `docs/release-notes/<版本>.md`、把 `CHANGELOG.md` 的版本段落补上、
在 `CHANGELOG.md` 里把该版本从「未发布」改成正式版本号，就完成了一次发版。

> 注意：改说明文件本身不会触发任何构建；
> 但**推 tag 一定会触发发版流程**（tag 事件不受路径过滤影响）。
